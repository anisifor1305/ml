# ИНЖЕНЕРНЫЙ ТРЕК (ПАРАЛЛЕЛЬНЫЙ)

## Сессии E1–E40 · Параллельно, месяцы 1–19

Инженерный трек идёт параллельно основной программе.

Его задача — не дать теории существовать отдельно от реального мира. Каждые 1–2 недели команда берёт знания, доступные на текущем этапе, и превращает их в работающий инженерный или research-артефакт.

Каждая инженерная сессия должна заканчиваться **проверяемым результатом**:

- работающим кодом;
    
- репозиторием;
    
- сервисом;
    
- экспериментом;
    
- отчётом;
    
- графиком;
    
- моделью;
    
- технической статьёй;
    
- воспроизводимым research-артефактом.
    

Фраза «мы разобрались» не считается результатом.

---

# Общий стандарт инженерной сессии

Для каждой E-сессии необходимо:

1. Создать issue / task с описанием цели.
    
2. Определить критерий завершения до начала работы.
    
3. Работать через отдельную ветку.
    
4. Сделать Pull Request.
    
5. Получить review хотя бы от одного участника команды.
    
6. Сохранить инструкции запуска.
    
7. Сохранить использованные версии зависимостей.
    
8. Сохранить результаты экспериментов.
    
9. Обновить README или документацию.
    
10. Добавить итог сессии в общий инженерный журнал.
    

Минимальная запись в журнале:

```text
E-сессия:
Дата:
Участники:

Цель:

Что сделали:

Что не получилось:

Какие решения приняли:

Какие метрики получили:

Какие проблемы нашли:

Что нужно улучшить позже:

Ссылка на PR:
Ссылка на артефакт:
```

# ФАЗА I — «ЧТО-ТО РАБОТАЕТ»

## E1–E6 · Месяцы 1–3

Цель фазы — пройти путь от пустого Git-репозитория до публично доступного AI-сервиса.

На этом этапе **не нужно обучать собственную модель**.

Используется готовая модель, потому что главная задача — освоить инженерный цикл.

## E1 — Командный ML-репозиторий и CI

### Цель

Создать единый репозиторий, в котором команда сможет работать следующие месяцы.

### Нужно получить

Репозиторий, который:

- клонируется на чистую машину;
    
- устанавливается одной последовательностью команд;
    
- имеет понятную структуру;
    
- автоматически проверяется CI;
    
- не позволяет сломанный код отправить в `main`.
    

### Структура

Создать минимум:

```text
project/
├── README.md
├── pyproject.toml
├── .gitignore
├── src/
├── tests/
├── configs/
├── scripts/
├── notebooks/
├── data/
└── .github/
    └── workflows/
```

`data/` не должна попадать в Git.

### Что сделать

1. Создать GitHub-репозиторий.
    
2. Настроить ветку `main`.
    
3. Запретить прямые изменения `main`.
    
4. Включить Pull Request workflow.
    
5. Настроить Python-окружение.
    
6. Зафиксировать версию Python.
    
7. Создать `pyproject.toml`.
    
8. Добавить линтер.
    
9. Добавить formatter.
    
10. Добавить минимум один unit-test.
    
11. Настроить GitHub Actions.
    
12. CI должен запускать:
    
    - установку зависимостей;
        
    - линтер;
        
    - тесты.
        
13. Намеренно создать PR с ошибкой.
    
14. Убедиться, что CI его блокирует.
    
15. Исправить ошибку.
    
16. Сделать первый зелёный merge.
    

### Проверка

Другой участник команды должен:

```bash
git clone ...
cd project
...
```

и получить работающий проект без ручных исправлений.

### Результат

**Репозиторий с зелёным CI.**

3. Зафиксировать:
    
    - название модели;

    - задачу;
        
    - вход;
        
    - выход.
        
4. Создать FastAPI-приложение.
    
5. Сделать endpoint:
    

```http
POST /predict
```

6. Добавить Pydantic-модель входных данных.
    
7. Добавить Pydantic-модель ответа.
    
8. Загружать ML-модель **один раз при старте приложения**.
    
9. Реализовать обработку ошибок.
    
10. Добавить:
    

```http
GET /health
```


# E10 — ML-тесты в CI

## Цель

Научиться автоматически обнаруживать поломку ML-кода.

### Добавить тесты

### Data tests

Проверять:

- shape;
    
- dtype;
    
- NaN;
    
- Inf;
    
- диапазоны;
    
- число признаков.
    

### Model tests

Проверять:

- shape output;
    
- отсутствие NaN;
    
- диапазон probabilities;
    
- сумма softmax ≈ 1.
    

### Behaviour tests

Например:

```text

→ positive probability > negative
```

### Regression test

Сохранить маленький validation dataset.

Если метрика падает сильнее заданного threshold — CI должен падать.

### Проверка

Намеренно сломать preprocessing.
