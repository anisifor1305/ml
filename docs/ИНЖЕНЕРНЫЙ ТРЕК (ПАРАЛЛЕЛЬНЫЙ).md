# ИНЖЕНЕРНЫЙ ТРЕК (ПАРАЛЛЕЛЬНЫЙ)

## Сессии E1–E42 · Строго раз в 2 недели · Недели 1–84 · Месяцы 1–19

---

## Что это такое

Инженерный трек — это **система аттестаций основной программы**, а не отдельный курс по DevOps.

Раз в две недели команда закрывает окно из 5–7 прошедших занятий и обязана превратить их в работающий артефакт. Ни одна E-сессия не вводит тему, которую ещё не прочитали на лекции. Ни одна лекция не остаётся без инженерного применения дольше двух недель.

Формула каждой сессии:

```text
теория последних 2 недель
        +
всё, что уже работает (кумулятивно)
        +
ровно один новый инженерный навык
        =
проверяемый артефакт
```

Фраза «мы разобрались» не считается результатом.

## Что изменилось относительно старой версии

| Было | Стало |
|---|---|
| E-сессии не привязаны к номерам занятий | Каждая сессия имеет **точку входа: «после занятия N»** |
| Инженерия жила отдельно от лекций | Каждая сессия **аттестует конкретное окно занятий** |
| Ритм «раз в 1–2 недели», на практике плавающий | **Жёстко раз в 2 недели**, 42 окна × 2 недели = 84 недели |
| Темы забегали вперёд лекций (эмбеддинги на 11-м месяце при лекции на 168-м занятии) | Порядок инженерных тем **подчинён порядку лекций** |
| 40 сессий | **42 сессии** — расширены участки, где одна старая сессия несла нагрузку трёх |
| Сложность росла «на глаз» | Сложность **размечена ★1–★5** и часами, рост монотонный |
| Проекты №1–№4 висели в календаре | Проекты **привязаны к границам блоков** программы |

**Сложность старой версии сохранена и не понижена.** Оценка калибровки старого трека: E1–E6 были ★1–★2, E7–E14 ★2–★3, E15–E22 ★3–★4, E23–E30 ★4, E31–E40 ★4–★5. Это правильная кривая, она перенесена один в один. Изменилось только то, **когда** задание встречается и **что именно** оно закрепляет. Ни одно задание не удалено: там, где старая сессия содержала работу на три подхода (E23–E26 по RAG, E11–E14 по Kaggle), она разложена по окнам, а не урезана.

## Общий стандарт инженерной сессии

Не меняется от E1 до E42.

1. Issue с целью и **критерием завершения, записанным до начала работы**.
2. Отдельная ветка.
3. Pull Request.
4. Review минимум от одного участника команды.
5. Инструкции запуска в README.
6. Зафиксированные версии зависимостей.
7. Сохранённые результаты экспериментов.
8. Обновлённая документация.
9. Запись в инженерном журнале.
10. **Регрессия запрещена:** всё, что работало в предыдущих сессиях, продолжает работать. Ломать прошлое ради нового нельзя.

### Запись в журнале

```text
E-сессия:            Дата:              Участники:
Окно занятий:        Новый навык:

Цель:
Что сделали:
Что не получилось:
Какие решения приняли:
Какие метрики получили:
Какие проблемы нашли:
Что нужно улучшить позже:

Ссылка на PR:        Ссылка на артефакт:
```

### Как принимается сессия

Три уровня, все три обязательны:

| Уровень | Вопрос | Кто проверяет |
|---|---|---|
| **Работает** | артефакт запускается на чистой машине по README | другой участник команды |
| **Закрепляет** | каждое занятие окна отражено в коде или отчёте | автор защищает устно, 10 минут |
| **Не сломало прошлое** | зелёный CI, прошлые артефакты живы | автоматика |

### Механика долга

Если сессия не сдана в срок — она **не переносится и не отменяется**. Она становится долгом и закрывается **параллельно** со следующей. Два непогашенных долга подряд — стоп основной программы на одну неделю. Иначе инженерный трек снова превратится в то, чем он был.

2. Чувствительность к сиду: разброс по 5+ сидам явно указан.
3. Устойчивость к шуму во входах и к сдвигу распределения.
4. **OOD-оценка:** проверка на данных из другого источника или другого домена. Честно записать, где метод перестаёт работать.
5. Если метод работает **только** на одном датасете — это результат, и он должен быть написан в Limitations.

**Статистика (занятие 234):**

1. Финальные числа: `mean ± std` + доверительные интервалы, минимум 5 сидов на конфигурацию.
2. Обоснованный статистический тест, размер эффекта, поправка на множественные сравнения.
3. Проверить мощность: достаточно ли прогонов, чтобы обнаружить заявленный эффект.
4. **Явно перечислить всё, что статистически незначимо.**

**Неожиданные результаты (занятие 235):** для каждого расхождения с ожиданием — расследование по протоколу: баг в коде / ошибка в данных / неверная метрика / неверная гипотеза. Проверить в этом порядке. Только исключив первые три, признавать четвёртое. Каждое расследование — в лабораторном журнале.

**Introduction (занятие 236):** написать по структуре «контекст → проблема → пробел → наш вклад → результаты». Каждое утверждение о вкладе должно указывать на конкретную таблицу или рисунок.

### Инженерная часть: conference-grade artifact

```text

scripts · checkpoints · dataset instructions
reproduction_commands.md · expected_results.md · hardware_requirements.md
```

README обязан отвечать буквально на эти вопросы:

```text

```

**Главная проверка:** отдать репозиторий человеку, не участвовавшему в проекте, и не отвечать на вопросы. Он должен самостоятельно воспроизвести минимум один основной результат. Всё, что ему пришлось угадывать, — дефект артефакта и подлежит исправлению.

# ИТОГ ИНЖЕНЕРНОГО ТРЕКА

К концу E42 участник проходит полный путь и умеет пройти его снова, в одиночку:

```text
идея → литература → пробел → гипотеза → протокол
→ данные → baseline → эксперименты → собственная модель
→ абляции → статистическая проверка → анализ ошибок
→ API → Docker → CI/CD → GPU → deployment → monitoring
→ evaluation → воспроизведение → research artifact → paper
```

### Три правила, которые не меняются от E1 до E42

**1. Каждая сессия закрепляет конкретные занятия.** Инженерный трек не существует отдельно от программы. Он существует, чтобы то, что прочитано на лекции, было применено в течение двух недель — пока оно ещё живое.

**2. Регрессия запрещена.** Всё, что работало в E5, обязано работать в E42. Портфолио — это не 18 отдельных проектов, а одна непрерывно растущая система.

**3. Любой заявленный результат должен быть измерим, воспроизводим и доступен для внешней проверки.**

Не так:

> «мы использовали PyTorch, Docker и RAG».

А так:

> «вот задача, вот baseline, вот изменение, вот метрика до и после, вот доверительный интервал по 5 сидам, вот код, вот commit, вот инструкция, по которой посторонний человек получает тот же результат».
