# Занятие 10. SQL: основы и соединения

## 1. Что мы запускаем

PostgreSQL — серверная программа, которая хранит таблицы и выполняет запросы.
SQL — язык запросов. psql — клиентская программа, которая передаёт SQL серверу
и показывает результат. Python сегодня не нужен для написания запросов:
готовый Python-скрипт только запускает проверки.

Docker — способ запускать PostgreSQL в контейнере с отдельной конфигурацией
и хранилищем. Это не другой SQL. Сейчас доступен отдельный локальный PostgreSQL;
Docker-конфигурация подготовлена, но Docker не установлен.

pandas загружает данные в процесс Python. PostgreSQL позволяет фильтровать,
соединять и выбирать нужные данные на стороне сервера, до передачи в Python.
Сервер читает данные с диска через буферы памяти, выбирает алгоритмы соединений
и сортировок. Его операции не обязаны выполняться в текстовом порядке запроса.

Почему это нужно для ML: пользователи, платежи и обращения часто хранятся
в отдельных таблицах. Нужно правильно извлечь строки и не размножить события.

## 2. Таблицы, строки, ключи

Реляционная модель представляет данные таблицами со столбцами и строками.
В SQL дубликаты строк результата разрешены. Порядок строк не гарантирован без ORDER BY.
Гранулярность — смысл одной строки: человек, платёж, пара человек/платёж.

Первичный ключ (PRIMARY KEY) однозначно определяет строку, уникален и не NULL.
Внешний ключ (FOREIGN KEY) связывает значение с ключом другой таблицы.
Он может повторяться: у одного человека несколько платежей. Если столбцу разрешён
NULL, внешний ключ также может быть NULL.

Схема — пространство имён для таблиц. lesson10.people означало бы таблицу people
в схеме lesson10. В практике используется lesson10, в примерах — lesson10_demo.

## 3. Таблицы для примеров

Это другие данные, не задания. В psql переключись:

```sql
SET search_path TO lesson10_demo;
```

SET search_path задаёт, в какой схеме искать имена таблиц без префикса.
В проверяющем скрипте схема lesson10 выставляется автоматически.

people — одна строка на человека:

| person_id | name | age | team_id | manager_id |
|---|---|---|---|---|
| 10 | Alina | 28 | 1 | NULL |
| 20 | Max | NULL | 2 | 10 |
| 30 | Olya | 35 | NULL | 10 |

teams — одна строка на команду:

| team_id | title |
|---|---|
| 1 | Research |
| 2 | Platform |
| 3 | Vision |

payments — одна строка на платёж:

| payment_id | person_id | amount |
|---|---|---|
| 201 | 10 | 100.00 |
| 202 | 10 | 300.00 |
| 203 | 20 | NULL |
| 204 | NULL | 50.00 |

## 4. Типы данных

INTEGER — целые значения, например идентификатор или возраст.
TEXT — текст переменной длины, например имя.
NUMERIC(10,2) — десятичное число: до 10 цифр всего, из них 2 после точки.
Подходит для сумм с точной десятичной арифметикой; это не float.
DOUBLE PRECISION — приближённое число с плавающей точкой.
BOOLEAN — TRUE/FALSE; также возможен NULL, если не запрещён.
DATE — календарная дата, например DATE '2026-10-24'.
TIMESTAMP — дата и время без часового пояса.
TIMESTAMPTZ — момент времени с учётом часового пояса; отображение зависит от настройки сессии.
NULL — отсутствие значения, а не самостоятельный тип и не ноль/пустая строка.

В psql команда `\d people` показывает столбцы, типы и ограничения.
CREATE TABLE создаёт структуру таблицы; INSERT добавляет строки.
Для этого занятия они уже выполнены инфраструктурой, писать их пока не требуется.

## 5. SELECT и FROM

SELECT перечисляет выходные столбцы. FROM указывает исходную таблицу.
Точка с запятой завершает SQL-команду. Запятые разделяют столбцы.

```sql
SELECT person_id, name
FROM people;
```

Результат содержит три пары: (10, Alina), (20, Max), (30, Olya).
Без ORDER BY порядок этих пар не гарантирован.
SELECT * означает все столбцы; при соединениях удобнее явно перечислять необходимые.
SQL-ключевые слова пишут заглавными для читаемости, это не обязательное требование.
Текстовые значения пишутся в одинарных кавычках: 'Alina'.
Двойные кавычки предназначены для имён объектов, например "CaseSensitiveName".
Комментарий начинается с -- и продолжается до конца строки.

## 6. WHERE: отбор строк

WHERE оставляет только строки, где условие истинно.
Операторы: = равно, <> не равно, > больше, >= не меньше, < меньше, <= не больше.
AND требует выполнения обоих условий; OR — хотя бы одного; NOT отрицает условие.
Скобками явно задавай порядок сложных условий.

```sql
SELECT person_id, name
FROM people
WHERE age >= 30;
```

Результат: (30, Olya). Max не попал, потому что его возраст неизвестен.

```sql
SELECT person_id, name
FROM people
WHERE name = 'Alina' OR age >= 30;
```

Результат: Alina и Olya. Это два независимых способа пройти фильтр.

## 7. NULL и три значения логики

Результатом сравнения может быть TRUE, FALSE или UNKNOWN — неизвестно.
Сравнение NULL = 28 не истинно и не ложно: возраст неизвестен.
Даже NULL = NULL даёт UNKNOWN, поскольку два неизвестных значения не обязаны совпадать.
WHERE пропускает только TRUE; FALSE и UNKNOWN отбрасываются.

Для проверки отсутствия значения есть IS NULL, для наличия — IS NOT NULL:

```sql
SELECT name FROM people WHERE age IS NULL;
```

Результат: Max. Запись age = NULL не заменяет IS NULL.

Логика с неизвестным:

| Выражение | Результат |
|---|---|
| TRUE AND UNKNOWN | UNKNOWN |
| FALSE AND UNKNOWN | FALSE |
| TRUE OR UNKNOWN | TRUE |
| FALSE OR UNKNOWN | UNKNOWN |
| NOT UNKNOWN | UNKNOWN |

Поэтому WHERE age <> 28 не выберет Max: неизвестное не означает «точно не 28».

## 8. ORDER BY и LIMIT

ORDER BY сортирует результат. ASC — по возрастанию, DESC — по убыванию.
NULLS LAST отправляет пропуски в конец; NULLS FIRST — в начало.
LIMIT n оставляет первые n строк результата.

```sql
SELECT person_id, name, age
FROM people
ORDER BY age DESC NULLS LAST, person_id ASC
LIMIT 2;
```

Результат:

| person_id | name | age |
|---|---|---|
| 30 | Olya | 35 |
| 10 | Alina | 28 |

Второй ключ person_id определяет порядок при одинаковом возрасте.
Без полного порядка LIMIT может выбирать разные строки среди равных значений.

Логическая последовательность для наших запросов:
FROM/JOIN → WHERE → SELECT → ORDER BY → LIMIT.
Это способ понимать результат, не обещание физического порядка работы сервера.

## 9. JOIN: сопоставление строк

JOIN соединяет строки таблиц. ON задаёт условие совпадения.
AS задаёт короткое имя (псевдоним). p.name — столбец name таблицы с псевдонимом p.

```sql
SELECT p.name, t.title
FROM people AS p
INNER JOIN teams AS t ON p.team_id = t.team_id
ORDER BY p.person_id;
```

Сервер формирует пары строк, удовлетворяющие ON. Результат:

| name | title |
|---|---|
| Alina | Research |
| Max | Platform |

Olya не имеет известной команды; Vision не имеет людей. INNER JOIN их не сохраняет.
Слово INNER можно опустить: JOIN без типа означает INNER JOIN.

## 10. LEFT, RIGHT и FULL JOIN

LEFT JOIN сохраняет все строки таблицы слева. Если совпадения справа нет,
столбцы правой стороны становятся NULL.

```sql
SELECT p.name, t.title
FROM people AS p
LEFT JOIN teams AS t ON p.team_id = t.team_id
ORDER BY p.person_id;
```

Результат: (Alina, Research), (Max, Platform), (Olya, NULL).

RIGHT JOIN сохраняет все строки справа. Для тех же таблиц:

```sql
SELECT p.name, t.title
FROM people AS p
RIGHT JOIN teams AS t ON p.team_id = t.team_id
ORDER BY t.team_id;
```

Результат: (Alina, Research), (Max, Platform), (NULL, Vision).

FULL JOIN сохраняет несовпавшие строки с обеих сторон:

```sql
SELECT p.name, t.title
FROM people AS p
FULL JOIN teams AS t ON p.team_id = t.team_id
ORDER BY p.person_id NULLS LAST, t.team_id;
```

Результат: (Alina, Research), (Max, Platform), (Olya, NULL), (NULL, Vision).
В обычном ON a.key = b.key два NULL не совпадают. Это отличается от pandas.merge,
который может сопоставлять пропуски ключей друг с другом.

## 11. Соединение не означает одну строку на человека

У Alina два платежа. При соединении people с payments у неё будут две строки:
(Alina, 201, 100), (Alina, 202, 300). Это ожидаемая гранулярность «человек/платёж».

Если у ключа слева m строк, справа n строк, и каждая пара проходит ON,
число совпавших строк — m × n. У двух покупок и трёх обращений одного человека
получится шесть пар. Последующее суммирование может повторно учесть покупки.

LEFT JOIN сохраняет число строк слева только если на каждую левую строку
приходится не более одного совпадения справа.
DISTINCT после SELECT удаляет одинаковые выходные строки. Он не исправляет
ошибочный смысл соединения и может скрыть отдельные события с одинаковыми значениями.

## 12. ON и WHERE при LEFT JOIN — разные действия

ON определяет, какие строки считать совпавшими. WHERE отбирает результат соединения.

```sql
SELECT p.name, t.title
FROM people AS p
LEFT JOIN teams AS t
    ON p.team_id = t.team_id AND t.title = 'Research'
ORDER BY p.person_id;
```

Результат: (Alina, Research), (Max, NULL), (Olya, NULL).
Все люди сохранены, но добавлена только команда Research.

Если условие t.title = 'Research' перенести в WHERE, останется только Alina.
Для строк с NULL сравнение даст UNKNOWN, и WHERE их отбросит.
Это одна из основных ловушек LEFT JOIN.

## 13. CROSS JOIN

CROSS JOIN создаёт все сочетания строк двух таблиц, без ON.
У трёх людей и трёх команд будет 3 × 3 = 9 сочетаний.

```sql
SELECT p.name, t.title
FROM people AS p
CROSS JOIN teams AS t
ORDER BY p.person_id, t.team_id;
```

Для Alina будут Research, Platform, Vision; то же для Max и Olya.
Это возможные сочетания, а не фактическое членство в командах.

## 14. SELF JOIN

SELF JOIN — соединение таблицы с самой собой. Отдельного ключевого слова SELF нет:
одна таблица используется под двумя псевдонимами.

```sql
SELECT employee.name AS employee, manager.name AS manager
FROM people AS employee
LEFT JOIN people AS manager ON employee.manager_id = manager.person_id
ORDER BY employee.person_id;
```

Результат: (Alina, NULL), (Max, Alina), (Olya, Alina).
Слева строка рассматривается как сотрудник, справа — как его руководитель.
AS в SELECT задаёт названия выходных столбцов; AS в FROM — псевдонимы таблиц.

## 15. Подзапрос и IN

Подзапрос — SELECT внутри другого SQL-запроса.
IN проверяет, равно ли значение хотя бы одному значению списка или результата подзапроса.

```sql
SELECT name
FROM people
WHERE team_id IN (
    SELECT team_id FROM teams WHERE title = 'Research'
)
ORDER BY person_id;
```

Внутренний запрос возвращает 1, внешний выбирает Alina.
Подзапрос для такого IN должен возвращать один столбец.
Порядок строк и повторы внутри IN не размножают строки внешней таблицы.
Это логическое объяснение; планировщик может физически выполнить запрос иначе.

## 16. EXISTS: достаточно существования строки

EXISTS(подзапрос) возвращает TRUE, если подзапрос нашёл хотя бы одну строку.
Его интересует наличие строк, а не выбранные в них значения.
Поэтому SELECT 1 внутри EXISTS — условная единица, не количество и не идентификатор.

```sql
SELECT p.name
FROM people AS p
WHERE EXISTS (
    SELECT 1
    FROM payments AS pay
    WHERE pay.person_id = p.person_id
)
ORDER BY p.person_id;
```

Результат: Alina и Max, по одному разу. У Alina два платежа, но EXISTS
не создаёт две выходные строки. Платёж Max учитывается, даже если amount неизвестна.

Подзапрос коррелированный: он ссылается на p.person_id из внешнего запроса.
Логически для каждого человека проверяется существование подходящего платежа;
это не утверждение о физическом цикле сервера.
NOT EXISTS истинен, когда подходящих строк нет. Для этого примера выбрал бы Olya.
Не существует общего правила «EXISTS всегда быстрее IN»: смотри смысл запроса и план.

## 17. Ловушка NOT IN и NULL

```sql
SELECT 10 NOT IN (20, NULL) AS absent;
```

Результат — NULL, то есть UNKNOWN. Почему:
«10 не равно 20» — TRUE, а «10 не равно неизвестному» — UNKNOWN.
TRUE AND UNKNOWN даёт UNKNOWN.

Если такое условие поставить в WHERE, строка не пройдёт.
NULL в списке не означает «игнорировать этот элемент».

Для требования «нет строки с таким ключом» часто удобно NOT EXISTS с явным
равенством ключей: NULL внутри таблицы не создаёт совпадения по обычному =.
Для IN/NOT IN и EXISTS/NOT EXISTS нужно сначала определить желаемую семантику NULL.

## 18. EXPLAIN: как сервер собирается выполнить запрос

EXPLAIN перед SELECT показывает план, обычно не выполняя сам SELECT.

```sql
EXPLAIN
SELECT person_id, name
FROM people
WHERE age >= 30;
```

План зависит от данных и настроек, конкретные числа заранее не фиксированы.
У маленькой таблицы может появиться Seq Scan с Filter.

Что означают элементы:

- Seq Scan — последовательный просмотр таблицы.
- Filter — условие, которому должны удовлетворять строки.
- Index Scan — чтение с использованием индекса, структуры для поиска значений.
- Sort — сортировка.
- Nested Loop — соединение с обработкой соответствующих строк второй стороны
  для строк первой стороны.
- Hash Join — соединение с хеш-таблицей по ключам.
- rows — оценка числа выходных строк узла, не фактическое число.
- cost — условная оценка стоимости, не секунды.

Читать дерево удобно от дочерних узлов к родительским: источник строк,
фильтрация/соединение, затем операции выше по дереву.
На маленьких таблицах Seq Scan вполне нормален.
EXPLAIN ANALYZE действительно выполняет запрос и добавляет фактические измерения.
Не нужно включать ANALYZE для нашей защиты: достаточно обычного EXPLAIN.
