# Лекция 01. Среда, Git и воспроизводимость с первого дня

Эта лекция не о том, как запомнить десять команд терминала. Она о дисциплине,
которая отличает «у меня один раз запустилось» от инженерной или
исследовательской работы. В ML эта разница особенно болезненна: результат
зависит не только от кода, но и от данных, версий библиотек, параметров
запуска, случайности, железа и того, в каком порядке человек нажимал ячейки
ноутбука.

## 1. Что именно значит воспроизводимость

Представь, что через три месяца модель показала accuracy 0.91. Само число почти
ничего не доказывает. Чтобы ему доверять, нужно суметь ответить на вопросы:

- какой commit кода дал этот результат;
- на какой версии данных он получен;
- как данные были очищены и разбиты на train/validation/test;
- с какими гиперпараметрами обучалась модель;
- какие версии Python, NumPy, PyTorch и CUDA использовались;
- какой был seed;
- как именно другой человек может повторить запуск.

Воспроизводимость — это способность повторить путь к результату, а не просто
сохранить файл с моделью. В минимальном учебном проекте достаточно пяти
составляющих:

```text
код + зависимости + данные/инструкция к данным + конфиг + команда запуска
```

В серьёзном эксперименте добавляются commit hash, логи, метрики, графики,
чекпоинты, информация о GPU и ограничения детерминизма. Но привычка начинается
с малого: новый проект должен запускаться не из памяти автора, а по README.

Типичная история «у меня работает» выглядит так. Первый человек запускал
ноутбук вчера, у него осталась переменная в памяти, а `pandas` установлен одной
версии. Второй клонировал код сегодня, запустил ячейки сверху вниз, получил
`ModuleNotFoundError` или другую метрику. Код внешне одинаковый, но окружение,
данные и состояние программы — нет.

Seed важен, но он не волшебная кнопка. `seed=42` повторяет псевдослучайность
только при одинаковом коде, данных, версиях библиотек и вычислительной среде.
Число 42 — культурный мем из «Автостопом по галактике», технического
преимущества у него нет. Подойдёт любое записанное целое число.

## 2. Python — это интерпретатор, а не просто команда `python`

Когда в терминале выполняется `python`, система ищет конкретный исполняемый
файл. На одном Mac могут одновременно жить системный Python, Python от
Homebrew, Python из Conda и Python из нескольких виртуальных окружений. У всех
могут быть разные версии и разные библиотеки.

Полезные команды диагностики:

```bash
python3 --version
which python3
python3 -m pip --version
```

`python3 --version` показывает версию интерпретатора. `which python3` отвечает
на более важный вопрос: *какой именно* интерпретатор будет запущен. Команда
`python3 -m pip` привязывает pip к тому же Python. Это безопаснее, чем просто
`pip install ...`, потому что на машине может быть несколько pip.

У Python есть две отдельные задачи:

1. Выбрать версию **интерпретатора**: Python 3.9, 3.11, 3.12 и так далее.
2. Изолировать **библиотеки проекта**: NumPy, pandas, PyTorch, pytest.

Для первой задачи существуют `pyenv` и Conda. Для второй — `venv`, Conda,
Poetry и uv. Они частично пересекаются, поэтому новичкам кажется, будто все
инструменты делают одно и то же. Это не так.

### `pyenv`

`pyenv` управляет версиями самого Python. Он полезен, когда один проект требует
Python 3.10, другой — 3.12, а системный Python вообще лучше не трогать. Пример
идеи:

```text
pyenv выбирает Python 3.12 для папки проекта
→ venv создаёт .venv на базе Python 3.12
→ pip устанавливает библиотеки в этот .venv
```

`pyenv` не заменяет виртуальное окружение. Он не хранит зависимости каждого
проекта изолированно; он выбирает базовый интерпретатор.

### `venv`

`venv` встроен в Python и создаёт отдельную папку с окружением проекта:

```bash
python3 -m venv .venv
source .venv/bin/activate
```

После активации `python` и `pip` указывают на `.venv`. Выход:

```bash
deactivate
```

В `venv` не происходит магии: это просто отдельный Python с отдельной папкой
`site-packages`. Поэтому он лучший инструмент для понимания основ. Текущий
учебный проект использует именно `.venv`.

### Conda

Conda одновременно управляет Python, окружениями и пакетами. Кроме Python-
пакетов она умеет ставить некоторые бинарные и системные зависимости. Поэтому
Conda часто встречается в научных проектах, особенно там, где есть CUDA,
специфические компиляторы или сложные библиотеки.

```bash
conda create -n ml python=3.12
conda activate ml
conda install numpy pandas
```

Conda удобна, но тяжелее `venv`: больше места, больше каналов пакетов, больше
способов получить конфликт версий. На старте не нужно заменять ей всё. Важно
понимать, что Conda-окружение — это другой изолированный мир; оно не обязано
видеть библиотеки из `.venv`.

### Poetry и uv

Poetry описывает Python-проект, зависимости и lock-файл. uv — современный
быстрый инструмент, который умеет создавать окружения и устанавливать
зависимости. Они удобны, когда основа уже понятна. Если сразу учить только
высокоуровневый инструмент, легко выучить ритуал команд, но не понять, где
живёт Python и почему библиотека не находится.

Практическое правило на старте: один проект — одна `.venv`; не смешивать
случайные глобальные установки с библиотеками проекта.

## 3. Зависимости: почему версия — часть результата

Зависимость — библиотека, от которой зависит твой код. У неё есть API, баги,
изменения и версия. Сегодня `pandas` может вести себя немного иначе, чем год
назад; PyTorch может менять доступные операции; библиотека может перестать
поддерживать старый Python.

Если написать только:

```text
numpy
```

то через месяц два человека могут установить разные версии. Это удобно для
экспериментальной библиотеки, но плохо для воспроизводимого результата.

Варианты фиксации:

```text
numpy                 # любая версия
numpy>=2.0            # не ниже 2.0
numpy>=2.0,<2.1       # только ветка 2.0.x
numpy==2.0.2          # ровно одна версия
```

Последний вариант называется pinning. Для упражнения, статьи и учебного
проекта он обычно предпочтителен: сначала важнее повторить запуск, чем получать
самые свежие обновления автоматически.

### `requirements.txt`

Это простой список пакетов:

```text
pytest==8.4.2
ruff==0.16.6
```

Установка:

```bash
python -m pip install -r requirements.txt
```

Плюс `requirements.txt` — простота. Минус — файл слабо описывает сам проект:
его имя, версию Python, dev-зависимости, настройки тестов и форматтера.

### `pyproject.toml`

Это современный стандартный конфигурационный файл Python-проекта. В нём можно
описать проект и настройки инструментов в одном месте:

```toml
[project]
name = "ml-learning"
requires-python = ">=3.10"
dependencies = ["numpy==2.0.2"]

[project.optional-dependencies]
dev = ["pytest==8.4.2", "ruff==0.16.6"]
```

`dependencies` нужны работе проекта, `dev` — разработке: тестам, линтерам,
форматтерам. В большом проекте также полезен lock-файл: он фиксирует не только
прямые пакеты, но и зависимости зависимостей.

Не нужно механически создавать и `requirements.txt`, и `pyproject.toml` в
каждой маленькой задаче. Выбери один понятный источник правды. В нашем
учебном репозитории пока достаточно `requirements.txt`; позже E1 потребует
проектный уровень с `pyproject.toml`.

## 4. Git: история решений, а не кнопка «сохранить»

Git хранит последовательность снимков проекта. Он не заменяет резервные копии
всех данных и не делает код хорошим, но позволяет увидеть, когда и почему
изменился проект.

Есть четыре важных понятия.

**Working tree** — текущие файлы на диске. **Staging area** — выбранные
изменения для следующего снимка. **Commit** — сохранённый снимок с сообщением.
**Repository** — история commits и веток.

Базовый цикл:

```bash
git status
git add path/to/file.py
git commit -m "feat: add dataset validation"
```

`git add` не публикует изменения и не создаёт commit. Он говорит: «в следующий
снимок войдут именно эти файлы». Это важно, потому что в рабочей папке могут
лежать черновик, отладочный лог и настоящее изменение.

`git commit` сохраняет историю локально. Он не отправляет код в GitHub. Для
отправки нужен remote и `git push`.

Хороший commit атомарен: одна законченная мысль. Например:

```text
feat: add dataset length validation
test: cover invalid dataset lengths
docs: document local setup
```

Сообщения вроде `update`, `fix`, `final2` не помогают будущему тебе понять
историю. Учебные conflict-commits могут называться проще, но привычку к ясному
сообщению стоит вырабатывать сразу.

### Ветки, merge и rebase

Ветка — независимая линия работы. `main` — стабильная основная ветка. Новая
задача делается в отдельной ветке, затем изменения попадают в `main` через
Pull Request и review.

```text
main ─── A ─── B
             \
feature        C ─── D
```

`merge` объединяет истории. Если два человека меняли одну и ту же строку по-
разному, Git не угадывает правильный текст и создаёт конфликт. Конфликт — не
авария, а честный вопрос к разработчику: какой вариант оставить?

`rebase` переносит commits текущей ветки поверх новой базы и делает историю
линейнее. Он полезен, но опаснее для уже опубликованных общих веток: меняет
историю commits. Пока безопасное правило простое: для совместной работы
понимай merge, а rebase используй только осознанно.

## 5. `.gitignore` и ML-данные

Git хорошо хранит исходный код, конфиги, маленькие текстовые файлы, README и
тесты. Он плохо подходит для тяжёлых данных, чекпоинтов и временных файлов.

Минимальный `.gitignore` для ML обычно содержит:

```text
.venv/
__pycache__/
.pytest_cache/
.DS_Store
.env
data/raw/*
data/processed/*
checkpoints/
artifacts/
```

`.venv` не коммитят, потому что она зависит от ОС и восстанавливается из
зависимостей. `__pycache__` — временные файлы Python. `.DS_Store` — мусор
Finder на macOS. `.env` часто содержит секреты.

Сырые данные обычно не коммитят по трём причинам: они большие, могут иметь
лицензионные ограничения и могут содержать личные данные. Вместо файла данных
в Git хранится инструкция: откуда скачать, как проверить версию и какой скрипт
подготовки запустить.

Но «игнорировать всё подряд» тоже ошибка. Небольшой пример данных, схема,
ссылка на датасет, data card и пустой `.gitkeep` полезны. `.gitkeep` — не
магический специальный файл Git; это просто обычный пустой файл, благодаря
которому Git сохраняет иначе пустую директорию.

Никогда не добавляй в commit реальные API-ключи, пароли, токены Hugging Face,
SSH-ключи и облачные credentials. Для шаблона допустим `.env.example`:

```text
API_KEY=
DATABASE_URL=
```

## 6. Структура ML-репозитория

Минимальная структура помогает не смешивать типы работы:

```text
project/
├── README.md
├── requirements.txt или pyproject.toml
├── .gitignore
├── src/
├── tests/
├── scripts/
├── notebooks/
├── configs/
├── data/
└── docs/
```

`src/` содержит переиспользуемый код: загрузку данных, признаки, модели,
метрики. `tests/` содержит автоматические проверки. `scripts/` — запускаемые
сценарии вроде `train.py`, `evaluate.py`, `download_data.py`. `notebooks/` —
исследования, графики и быстрые проверки гипотез. `configs/` хранит параметры
экспериментов отдельно от кода. `docs/` — конспекты, решения, инженерный
журнал и объяснения.

Папка `exercises/` в учебном репозитории тоже оправдана: это не библиотечный
код и не production-скрипты, а решения задач по занятиям. Не стоит насильно
помещать всё в `src/` только потому, что структура «выглядит серьёзно».

С ростом проекта появляются `models/`, `reports/`, `artifacts/`, но структура
должна обслуживать проект, а не быть украшением. Пять пустых папок полезнее,
чем двадцать папок с непонятными обязанностями, только если они отражают
реальную работу.

## 7. README — контракт с будущим человеком

README должен отвечать на вопросы человека, который ничего не знает о проекте:

1. Что делает проект?
2. Какая версия Python нужна?
3. Как создать окружение и установить зависимости?
4. Где взять данные?
5. Как запустить основной сценарий?
6. Как запустить тесты?
7. Какой результат ожидать?
8. Какие есть ограничения?

Для маленького упражнения README может состоять из десяти строк. Для
исследовательского репозитория он становится частью доказательства
воспроизводимости. Цель — не «красиво написать текст», а убрать необходимость
угадывать команды.

Плохой README:

```text
My ML project. Uses Python and PyTorch.
```

Полезный README:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python scripts/train.py --config configs/baseline.yaml
python -m pytest
```

После команд нужны ожидаемый результат и ограничения: сколько занимает запуск,
какие данные требуются, нужен ли GPU. README — не рекламная страница, а
инструкция для воспроизведения.

## 8. Jupyter-ноутбук и скрипт решают разные задачи

Ноутбук хорош для исследования: посмотреть первые строки таблицы, нарисовать
график, быстро попробовать гипотезу, объяснить ход анализа. Он плох как
единственный источник воспроизводимого пайплайна, потому что хранит скрытое
состояние ядра.

Можно выполнить ячейку 17, затем 4, потом вручную изменить переменную и
получить картинку, которую невозможно повторить при запуске сверху вниз.
Поэтому важный результат должен пережить «Restart Kernel + Run All».

Скрипт лучше для повторяемого запуска:

```bash
python scripts/train.py --config configs/baseline.yaml
```

Он получает параметры явно, стартует с чистого состояния и должен сохранить
артефакты в заранее понятное место. Обычный рабочий цикл выглядит так:

```text
ноутбук: исследовать данные и гипотезу
→ функция в src/: вынести повторяемую логику
→ script: сделать воспроизводимый запуск
→ test: проверить важные свойства
```

Не нужно воевать с ноутбуками. Плохо не наличие ноутбука, а ситуация, когда
единственный путь получить результат — запустить личный ноутбук автора в
неизвестном порядке.

## 9. Что считать хорошим стартом проекта

На первом проходе не требуется Docker, Kubernetes, облачная база и идеальный
CI. Нужен честный минимум:

```text
одна понятная папка проекта
одна версия Python
одно изолированное окружение
один файл зависимостей
одна инструкция запуска
одна история Git
```

Дальше дисциплина наращивается. Во время E1 появятся CI, PR, проверка стиля и
тесты. В следующих блоках — конфиги экспериментов, seed, GPU, трекинг метрик,
данные и деплой. Но фундамент один: любой заявленный результат должен иметь
понятный путь от чистой машины до полученного вывода.

## 10. Короткий список привычек

- Перед установкой пакета проверь, какой Python и pip используешь.
- Для проекта ставь библиотеки в `.venv`, не «куда-то в систему».
- Фиксируй версии, если результат должен повториться.
- Не коммить данные, веса, временные файлы и секреты без причины.
- Делай маленькие осмысленные commits.
- Не бойся конфликтов Git: это вопрос выбора правильной версии текста.
- Называй папки по роли, а не по настроению.
- Исследуй в ноутбуке, но важный запуск переноси в скрипт.
- Пиши README так, будто проект откроет ты сам через полгода.
- Сначала добивайся воспроизводимого минимального результата, потом усложняй
  инфраструктуру.

Главная мысль занятия: воспроизводимость — не отчёт, который пишут в конце.
Это способ работать с первого файла. Когда она встроена в процесс, исследовать
быстрее: ошибки легче локализовать, эксперименты легче сравнивать, а старые
результаты не превращаются в легенды без кода.
